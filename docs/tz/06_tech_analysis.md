# 06. Технический анализ и выбор стека

> Бриф (Р10) поручает исполнителю самостоятельно оценить Unity, Godot 4 и другие технологии и обосновать выбор. Здесь — анализ, оценка вариантов и итоговое решение. Факты о версиях и требованиях магазинов сверены на 2026-10-18; перед стартом разработки их нужно перепроверить (спайки §11).
>
> **Решения релиза 1:** физика — собственный детерминированный решатель на C# в ядре, Box2D v3 — для будущих режимов (Р23, §6.5); обмен кадрами с нативным кодом — RGBA/BGRA (Р24, §6.4); Unity-код компилируется только в CI (Р26, §6.7). Выбор движка (§6.3) эти решения не меняют.

## 6.1. Что определяет выбор

Технический облик Ballverse задают шесть задач. Выбор стека — это выбор того, где каждая из них решается дешевле и надёжнее.

| # | Задача | Почему трудная | Вес |
|---|---|---|---|
| T1 | **Физика**: сотни–тысячи тел, 60 FPS на среднем телефоне, детерминизм на одном устройстве | Режимы roadmap M09, M15 — до 1500–3000 тел; генерация прогоняет 8–24 симуляции за секунды (§2.4) | 20 |
| T2 | **Рендеринг** 2D с эффектами (SDF-шары, следы, свечение, частицы, метаболы) и офлайн-рендер в 1080p | Один и тот же кадр рисуется в реальном времени и в экспорт | 10 |
| T3 | **Видео**: аппаратное декодирование видео пользователя, кодирование H.264/AAC, MP4, HDR → SDR | Нет кроссплатформенного готового решения; FFmpegKit закрыт (§6.4) | 15 |
| T4 | **SDK монетизации и аналитики**: AdMob + UMP, StoreKit 2, Play Billing 8+, Firebase | Должны быть официальные, поддерживаемые плагины, иначе каждое требование магазинов — наша проблема | 10 |
| T5 | **Интерфейс**: сложный редактор, листы, жесты, стеклянные материалы | Редактор — это «приложение», а не игровой HUD | 10 |
| T6 | **Трудоёмкость** разработки и поддержки на двух платформах | Одна кодовая база против двух нативных | 15 |
| T7 | **Инструменты и CI**, удобство для разработки ИИ-агентом (как в Raivon) | Текстовые форматы, headless-сборки, тесты без редактора | 10 |
| T8 | **Стоимость и размер** (лицензия, размер сборки) | Мобильные пользователи чувствительны к размеру | 5 |
| T9 | **Зрелость и риск** (сообщество, вакансии, долгосрочная поддержка) | Коммерческий продукт на годы | 5 |

| Вариант | Состав |

## 6.4. Видео: нативные кодеки вместо FFmpeg

Бриф упоминает «FFmpeg-подобные решения». Анализ показывает, что FFmpeg для Ballverse — **не лучший выбор**:

| Фактор | FFmpeg (через обёртку) | Нативные API (выбрано) |
|---|---|---|
| Поддержка обёртки | **FFmpegKit официально закрыт** (2025), готовые сборки удалены из репозиториев; остались форки сообщества без гарантий | AVFoundation (iOS) и MediaCodec/Media3 (Android) поддерживаются Apple и Google |
| Скорость кодирования | Программный x264 медленный и греет телефон; аппаратные кодеры через FFmpeg на мобильных — частично | Аппаратные кодеры (VideoToolbox, MediaCodec) — в разы быстрее и экономичнее |
| Лицензия | LGPL/GPL (x264 — GPL): риски для закрытого коммерческого приложения в App Store, требования динамической линковки | Нет лицензионных ограничений |
| Размер | +20–60 МБ на архитектуру | 0 (системные библиотеки) |
| HDR, повороты, VFR с iPhone | Нужно настраивать самим | Системный декодер знает свои же форматы |
| Единый код на две платформы | Да | Нет: два модуля (релиз 1 — ObjC++ и Java, позже Swift и Kotlin), но тонких — только декодер, кодер, мультиплексор (§7.5) |

### Релиз 1: кадры RGBA (Р24)

Через границу Unity ↔ нативный код в релизе 1 ходят кадры **RGBA32** (8 бит на канал, строки сверху вниз, плотно упакованы), а не YUV. Перестановку каналов в BGRA для iOS делает нативный код, поэтому C#-сторона одинакова на обеих платформах:

| Направление | iOS (ObjC++, AVFoundation) | Android (Java, `android.media`) |
|---|---|---|
| Экспорт: Unity → кодер | `AsyncGPUReadback` в `RGBA32` → копирование с перестановкой RGBA→BGRA в `CVPixelBuffer` (`kCVPixelFormatType_32BGRA`) из пула `AVAssetWriterInputPixelBufferAdaptor` → `AVAssetWriter` (H.264, VideoToolbox сам преобразует в YUV) | `AsyncGPUReadback` в `RGBA32` → прямой `ByteBuffer` над памятью кадра без копирования через JNI → текстура GLES → отрисовка во входную `Surface` кодера `MediaCodec` (`createInputSurface`, EGL14, `eglPresentationTimeANDROID`); преобразование в YUV делает аппаратура. Запасной путь: CPU-преобразование в YUV и `getInputImage` |
| Импорт: декодер → Unity | `AVAssetReader` с выводом `32BGRA` и SDR-видеокомпозицией (BT.709), перестановка в RGBA, масштаб до размера слота | `MediaExtractor` + `MediaCodec`-декодер → `ImageReader` (`YUV_420_888`; для HDR без системного тонмаппинга — `YCBCR_P010`, API 31+) → CPU-преобразование в RGBA с поворотом, обрезкой, масштабом и тонмаппингом HDR (§7.5) |

- Почему: это самый простой путь, который работает одинаково на всех устройствах (вход кодера через `Surface` поддерживается с Android 4.3, BGRA-буферы — во всех версиях iOS), не требует compute-шейдеров и сводит фрагментацию цветовых форматов кодеков (R5) к минимуму. Цена — больше трафика памяти (1080×1920×4 ≈ 8,3 МБ на кадр против ≈ 3,1 МБ у NV12), что приемлемо для офлайн-экспорта.
- Ориентация строк одна — сверху вниз; если графический API читает кадр снизу вверх, к ней приводит компоновщик кадра перед чтением (флага `flipY` в API писателя нет).
- **Позже:** преобразование RGB→NV12 compute-шейдером, YUV-текстуры для видео пользователя, «нулевое копирование» (§7.5), горячий путь на C++ NDK. Включаются, если замеры экспорта на устройствах не укладываются в цели §3.8.

**Почему компоновка кадра в движке, а не в нативном редакторе.** Media3 Transformer и AVFoundation умеют накладывать видео (картинка в картинке), но: (1) это две разные реализации раскладок, текста и эффектов, которые будут расходиться между iOS, Android и предпросмотром; (2) у Media3 Composition есть ограничения (например, нельзя начать последовательность со смещением — а сдвиг видео относительно симуляции нужен, §3.4); (3) кадр симуляции всё равно рисует движок. Поэтому кадр целиком собирает движок, а нативный слой только декодирует и кодирует. Предпросмотр и экспорт совпадают по построению (§3, принцип студии).

## 6.5. Физика: собственный решатель в релизе 1, Box2D v3 — для будущих режимов

### Решение для релиза 1 (Р23)

Физику трёх режимов релиза 1 считает **собственный детерминированный 2D-решатель** `Ballverse.Core.Sim` — чистый C# внутри ядра `Ballverse.Core`, без UnityEngine (§7.3).

| Причина | Пояснение |
|---|---|
| **Проверяется в контейнере** | Unity-редактора в среде разработки нет, Unity-код компилируется только в CI (Р26). Решатель на чистом C# собирается и тестируется `dotnet test` на каждом коммите: детерминизм, отсутствие «пролётов», бенчмарки шага — до первой сборки на устройстве |
| **Детерминирован по построению** | Один поток на мир, фиксированный тик, стабильный порядок обхода, собственный ГСЧ, своя тригонометрия — недетерминизму неоткуда взяться (правила §7.4). Реплеи, генерация (§2.4) и экспорт опираются на это напрямую |
| **Снимает риски R2 и R3** | R2 (новый API `LowLevelPhysics2D` нестабилен) в релизе 1 не возникает; R3 (нарушение детерминизма) ловится тестами в контейнере, а не на устройстве |
| **Простая геометрия режимов** | M01, M02, M05 — это шары против кинематических вращающихся дуг, отрезков и платформ плюс столкновения шар–шар. Стопок, соединений и столкновений многоугольник–многоугольник нет — вся мощь Box2D (SIMD-решатель, устойчивые стопки, соединения) здесь не нужна |

**Возможности решателя релиза 1:**

| Возможность | Требование |
|---|---|
| Тела | Динамические круги (шары: масса ∝ r², вращение для закрутки); кинематические и статические коллайдеры: отрезок с толщиной (капсула), цепочка капсул (многоугольник, звезда), аналитическое кольцо с прорезями (кромки — полукруглые торцы), диск, **платформа башни** M05 (`SpinPlatform`: вертикальный разрез вращающейся платформы, точка с локальным *x* относится к азимуту `asin(x / R) − θ`; сплошная вне просветов, событие удара сообщает азимут) |
| Кинематика | Поворот вокруг опорной точки с угловой скоростью ω, радиальное масштабирование (сжатие колец, пульс и эволюция фигуры); скорость точки стенки входит в отклик контакта |
| Шаг | Фиксированный тик 1/60 с, **8 подшагов по умолчанию** (подшаг 1/480 с; режим задаёт 4–16, предел валидации — 64); полунеявный метод Эйлера |
| Контакты | Шар–стенка: импульс с упругостью и трением Кулона; шар–шар: импульс с упругостью, мягкая позиционная коррекция перекрытия. Ограничение `maxSpeed` после каждого подшага; действующий предел — `max(maxSpeed; v_wall,max + 5 м/с)`, где `v_wall,max` — наибольшая скорость поверхности стенки в досягаемой зоне, чтобы ограничение не делало шар медленнее толкающей его стенки |
| Непрерывность | Свип-тест центра шара против стенок, расширенных на радиус шара, в системе отсчёта стенки на каждом подшаге. **Конверт скоростей:** скорость шара ≤ 60 м/с; угловая скорость стенки ≤ 360 °/с с учётом законов скорости (пульс, реверс); скорость поверхности стенки в зоне, досягаемой шарами, ≤ 25 м/с; радиальная скорость кинематического сжатия ≤ 5 м/с. Режимы обязаны ограничивать параметры этим конвертом (§2.9). Требование: **0 пролётов** во всём конверте при радиусе шара ≥ 0,05 м и толщине стенки ≥ 0,04 м (свойство-тест на 10 000 случайных бросков, включая худшие углы: 360 °/с и 25 м/с на краю, 60 м/с у шара, сжатие 5 м/с) |
| Широкая фаза | Равномерная сетка для шар–шар с детерминированным порядком ячеек; стенки проверяются по ограничивающим окружностям |
| События | Удар о стенку (`Hit`), удар шар–шар (`BallHit`), вход и выход из сенсора; импульсы за тик суммируются по паре; порядок событий стабилен — сортировка по (вид, A, B) |
| Детерминизм | Без `Dictionary`/`HashSet`-обхода, без параллелизма внутри мира, без `System.Math.Sin/Cos` в логике — собственные `SimMath` (таблица + полином), `sqrt` (точный по IEEE 754) |
| Производительность | Бюджеты тел §2.9; ориентир для CI: шаг сцены с максимальным бюджетом тира A при подшагах по умолчанию (8) ≤ 0,5 мс на тик на раннере x64 (прокси); если не укладывается — режим снижает число подшагов в пределах конверта или бюджет тел, подтверждение на устройствах — день 6 плана §11.2 |

**Границы детерминизма.** Требуется совпадение на **одной сборке и одном устройстве** (как и прежде). Результаты `dotnet test` (x64, .NET) и сборки IL2CPP на ARM64 могут расходиться в младших битах: компилятор C++ вправе сливать умножение и сложение (FMA). Поэтому «золотые» хэши из CI с устройством не сравниваются; на устройстве проверяется повторяемость (два прогона одного сида и пересчёт реплея, §8.5). Межустройственный детерминизм не обещается.

### Box2D v3 — для будущих режимов

- **Box2D v3** (Erin Catto, 2024–2025) — переписанный движок: SIMD-решатель, многопоточность, «мягкий шаг» (soft step), устойчивые стопки, непрерывные столкновения, кроссплатформенный детерминизм. Для режимов с твёрдыми телами это лучший доступный 2D-движок.
- В **Unity 6.3 LTS** появился низкоуровневый API 2D-физики на Box2D v3 (`UnityEngine.LowLevelPhysics2D`, точка входа `PhysicsWorld`): несколько изолированных миров параллельно, работа без игровых объектов, совместимость с Jobs/Burst. Он не связан со старыми компонентами `Rigidbody2D`/`Collider2D`.
- **Когда возвращается:** в волне 3 roadmap (§2.11, §11.4) — для режимов, которым нужны стопки, соединения, составные твёрдые тела или тысячи тел: M06, M09, M11, M12 (и, по итогам спайка, M15). Перед волной — спайк S1 (§11.4): `LowLevelPhysics2D` против Box2D v3 как нативной библиотеки через P/Invoke (код C, лицензия MIT); запасной путь — классическая 2D-физика Unity.
- В релизе 1 мир решателя — конкретный класс `PhysicsWorld` без интерфейса (лишняя абстракция до появления второго бэкенда не нужна). К волне 3 из него выделяется интерфейс `IPhysicsWorld`, и Box2D реализует тот же интерфейс (§7.3); реплей уже хранит `physicsBackend` (§7.4), поэтому режимы релиза 1 не переписываются при появлении второго бэкенда. Режим выбирает бэкенд один раз и не меняет его без повышения `SimVersion`.

## 6.6. Интерфейс и Liquid Glass

- **UI Toolkit** (UXML + USS — текстовые форматы, похожие на HTML/CSS) — основной фреймворк интерфейса: хорошо подходит для списков, листов, форм редактора; текстовые файлы удобны для ревью и для ИИ-агента; поддерживает темы через переменные USS.
- **Стеклянный материал** (§4.5) реализуется собственным шейдером, который читает общий размытый буфер сцены. Нужно проверить в проверке S3 (§11.2, дни 2 и 5), достаточно ли возможностей UI Toolkit в выбранной версии Unity для пользовательских материалов элементов; запасной вариант — стеклянные подложки рисуются отдельным слоем (uGUI/рендер-проход под UI Toolkit), а содержимое панели — UI Toolkit поверх.
- **Настоящий системный Liquid Glass** (iOS 26) доступен только в нативных вариантах D/E. Цена — второй интерфейс. Решение: 1.0 на собственном материале; вариант E пересматривается, если владелец решит, что нативный Liquid Glass критичен для бренда (вопрос В17).

## 6.7. Разработка и CI

Если Ballverse, как и Raivon, разрабатывает ИИ-агент (вопрос В13), Unity требует дисциплины, которая заодно полезна и людям:

1. **«Код прежде сцен».** Минимум сцен (одна загрузочная + одна основная), префабы и экраны собираются из кода и UXML. Двоичных и трудно читаемых YAML-правок — минимум.
2. **Чистое C#-ядро без UnityEngine** (`noEngineReferences`): параметры, генераторы, оценка зрелищности, права, рекламные правила, модель проекта, формат реплея, таймлайн. Тестируется обычным `dotnet test` без Unity — быстро, в любом контейнере (§7.3).
3. **Unity Test Framework** (EditMode/PlayMode) в batchmode для физики, рендера и офлайн-экспорта — в CI.
4. **CI:** GitHub Actions + GameCI (сборка Android `.apk` для установки напрямую и `.aab` для Google Play на Linux; экспорт Xcode-проекта и сборка/подпись iOS на macOS-раннере через fastlane, выкладка в TestFlight и Google Play internal testing). Секреты лицензии Unity — в GitHub Secrets.
5. **Нативные плагины.** Релиз 1: исходники ObjC++ (iOS) и Java (Android) внутри Unity-проекта (`Assets/Plugins/iOS`, `Assets/Plugins/Android`) собираются штатными сборками Xcode и Gradle — без отдельных проектов. Позже — отдельные проекты в репозитории со своими модульными тестами (XCTest, JUnit/инструментальные на эмуляторе).

**Ограничения среды разработки релиза 1 (Р26).** В контейнере разработки Unity-редактора нет (хосты Unity закрыты сетевой политикой). Следствия:

- Unity-код компилируется **только в GitHub Actions (GameCI)**, после того как владелец добавит секреты лицензии Unity (`UNITY_LICENSE` или `UNITY_EMAIL`/`UNITY_PASSWORD`/`UNITY_SERIAL`). Цикл «правка → компиляция» для Unity-слоя — минуты CI, а не секунды.
- Поэтому Unity-код пишется консервативно: только давно стабильные API Unity 6 (никаких экспериментальных и preview-пакетов, никаких API, появившихся в последних минорных версиях), минимум сцен и префабов, всё собирается из кода.
- Вся логика, которую можно выразить без движка, — в `Ballverse.Core` и проверяется `dotnet test` в контейнере; Unity-слой тонкий: адаптеры ввода, рендер, звук, сервисы, нативные мосты.
- Поведение на устройстве (кодеки, реклама, покупки, производительность) проверяет владелец на своих телефонах по чек-листу §8.6.

## 6.10. Когда пересмотреть решение

| Сигнал | Пересмотр |
|---|---|
| Режиму roadmap нужны стопки, соединения или тысячи тел, либо шаг `Core.Sim` не укладывается в бюджет | Выделить `IPhysicsWorld`, Box2D v3 за ним (волна 3, §2.11) |
| Спайк S1 (волна 3): Box2D v3 API Unity нестабилен или медленнее нативного Box2D v3 более чем в 1,5 раза | Box2D v3 как нативная библиотека через P/Invoke |
| Экспорт 1080p60 на устройстве (день 3–4 плана §11.2) на тире B дольше 2× длительности ролика | NV12 на GPU и нулевое копирование кадров (iOS: `CVMetalTextureCache`/IOSurface; Android: рендер прямо во входную поверхность кодера через общий EGL-контекст) — запланированы после релиза 1, переносятся раньше |
| Проверка S3 (§11.2): стеклянный материал > 3 мс на тире B или невозможен в UI Toolkit | Стекло отдельным слоем (§6.6) |
| Владелец решает, что системный Liquid Glass обязателен | Вариант E (нативная оболочка + Unity as a Library) для 2.0 |
| Выручка/финансирование > $200 000 за 12 мес. | Перейти на Unity Pro (учесть в бюджете) |
